Вопрос 1 · коротко

Каждое утро сценарий забирает транзакции парка из Fleet API за вчерашний день (постранично, повторяет запрос при 429). Он проверяет каждую строку и записывает данные в PostgreSQL через upsert по id транзакции, поэтому повторный запуск ничего не задваивает. Битые строки откладываются в отдельную таблицу с причиной. Каждый запуск пишется в журнал etl_runs. При ошибке срабатывает отдельный сценарий: он помечает запуск в журнале и шлёт алерт со ссылкой на перезапуск за нужную дату.

Вопрос 1

Сверка транзакций парка: Fleet API → PostgreSQL → отчёт

У партнёра Яндекс Такси с 40 000 водителей типичная ручная работа — каждый день сверять, что пришло из Fleet API, и считать итоги по водителям. Этот процесс я и собрал.

Схема · 12 узлов + сценарий ошибокn8n 1.123 · PostgreSQL 14+
Каждый день 06:00 МСКSchedule Trigger, часовой пояс задан в настройках сценария
Перезапуск за датуWebhook GET …/fleet-txn-rerun?date=2026-10-24 — для ручного догона
ПараметрыДата: из запроса или «вчера по Москве». Неверный формат и незакрытый день сразу дают ошибку
Журнал: стартetl_runs: запуск = id выполнения n8n, статус running
Fleet API: транзакцииPOST, пагинация по cursor, 300 мс между страницами, 4 попытки с паузой 5 с, ключ в credentials
Нормализация и проверкаВсе страницы в одну пачку. Нет водителя или сумма не число — строка откладывается с причиной. Дубли по id убираются. 0 транзакций — стоп, база не трогается
Запись в PostgreSQLОдин запрос: jsonb_to_recordset + ON CONFLICT (txn_id), считает новые, изменённые и без изменений
Журнал: готовоok и цифры: получено / новых / изменилось / отложено
Итоги дня по водителямGROUP BY driver_id за дату
ОтчётТекст сводки и строка для таблицы

Отчёт в TelegramСводка, топ водителей, предупреждение об отложенных строках
Откуда данные
Fleet API Яндекс Про, /v2/parks/transactions/list за прошедшие сутки по Москве. Заголовки X-Client-ID и X-Park-ID берутся из переменных окружения, X-API-Key хранится в credentials n8n, в JSON сценария секретов нет.
Этапы
Параметры → журнал → выгрузка всех страниц → проверка каждой строки → upsert → журнал → итоги → таблица и Telegram.
Где результат
  • fleet_txn — транзакции, ключ txn_id;
  • fleet_txn_rejected — отложенные строки с причиной и исходным JSON, ничего не теряется молча;
  • etl_runs — журнал запусков;
  • строка дня в Google-таблице и сообщение в Telegram.
Ошибки
  • сеть, 429 и 5xx: 4 попытки с паузой 5 с;
  • битые строки не роняют запуск, а уходят в fleet_txn_rejected, в отчёте видно сколько;
  • подозрительный ответ (0 транзакций, ответ без transactions) роняет запуск до записи в базу;
  • любое падение запускает отдельный сценарий ошибок: etl_runs.status = 'error' с текстом и узлом, плюс алерт в Telegram со ссылкой на выполнение и готовой командой перезапуска.
Повторные запуски
Запуск за ту же дату безопасен: ON CONFLICT (txn_id) DO UPDATE … WHERE значения отличаются. Совпавшие строки не трогаются, изменённые обновляются, отчёт пишет, сколько каких. Строка в таблице обновляется по дате. Пропущенный день догоняется вебхуком с ?date=. Сегодняшний и будущие дни сценарий не принимает.
В тесте вместо настоящего Fleet API стоял мой локальный сервер, он отдаёт ответы той же формы. Поля взяты из документации Fleet API, на вашем ключе сверю их в первый же день. Узлы Google Sheets и Telegram в тесте были выключены: им нужен ваш доступ. Остальное проверено на n8n 1.123 и PostgreSQL 18.

Что меняет

Добавляет и обновляет строки в трёх таблицах. Чужие данные не удаляет, схему не трогает.

Как проверить

etl_runs: статус ok, получено = новых + изменилось + без изменений + отложено. Сумма за день в отчёте совпадает с sum(amount) в базе.

Что может сломаться

Fleet API поменяет формат или лимиты. Ключ отзовут. День может выгрузиться не полностью, если API отдаст часть страниц.

Как восстановить

Алерт назовёт узел и дату. Чиню причину и перезапускаю дату вебхуком: upsert сам дотянет недостающее без дублей.

fleet-txn.workflow.json fleet-txn-errors.workflow.json schema.sql

Как поставить: выполнить schema.sql, импортировать оба JSON, создать три credentials (Postgres, Header Auth с X-API-Key, Telegram) и задать переменные FLEET_PARK_ID, FLEET_CLIENT_ID, REPORT_SHEET_URL, REPORT_CHAT_ID, ALERT_CHAT_ID. В n8n 2.x доступ к $env по умолчанию закрыт, там эти значения лучше вынести в узел «Параметры».

Пагинация n8n молча глотает 429

Первый прогон завершился «успешно» с пустыми данными. Остановила его только моя проверка «0 транзакций». В исходниках n8n нашёл причину: код ответа проверяется, только если пагинация продолжается. Ответ 429 без cursor считается последней страницей, поэтому повтор не срабатывает. Исправил условием завершения:

completeExpression:
  {{ $response.statusCode < 300 && !$response.body.cursor }}

Теперь 429 идёт в повтор. Для надёжности ответ без transactions отдельно роняет запуск.

Ссылки $('Узел') в HTTP Request приходили пустыми

Тело запроса и заголовки, собранные через $('Параметры').first().json…, вычислялись в пустоту: «JSON parameter needs to be valid JSON», X-Park-ID = undefined. Как проверил, через $json всё работает. Переделал сценарий: каждый узел передаёт дальше ровно то, что нужно следующему (Postgres через RETURNING). Поток данных стал виден по самим узлам, без скрытых ссылок через полсхемы.

Что доделал бы на рабочем стенде

401 и 403 повторять бессмысленно: сейчас n8n повторяет любую ошибку, и на неверном ключе уходит 16 секунд. Ещё добавил бы блокировку параллельного запуска за одну дату (pg_try_advisory_lock) и сверку итога дня с балансом из Fleet API, а workflow хранил бы в Git: экспорт по расписанию даёт историю изменений.

Первая неделя

Как я принимаю автоматизации от подрядчика

В вакансии сказано, что n8n и боты переходят к вам от подрядчиков. До первой правки я делаю так:

  • ОписьВсе workflow: что запускает, куда пишет, когда последний раз срабатывал и чей это процесс. Неактивные и дубли помечаю, сразу не удаляю.
  • Доступы и секретыКакие credentials за что отвечают и чьи это аккаунты. Токены подрядчика в первую очередь меняю на ключи компании.
  • Бэкап до правокЭкспорт всех workflow и credentials (зашифрованно) в Git, дамп базы n8n. Любую правку можно откатить.
  • Сценарий ошибокПроверяю, что у каждого важного workflow есть Error Workflow с алертом. Падение не должно оставаться незамеченным.
  • БотыГде работают (VPS, Docker, systemd), как перезапускаются, куда пишут логи, кто владелец токена в BotFather.
  • Карта процессовОдна страница: процесс → workflow → таблицы и боты → кто пользуется. С ней разбирать задачи из голосовых быстрее.
  • Правки по однойКаждая правка проходит четыре вопроса из вашей вакансии: что изменилось, как проверить, что может сломаться, как восстановить. Ответы записываю в описании workflow или коммита.
  • Claude и CodexИспользую каждый день для разбора чужого кода и документации. За результат отвечаю сам: объясняю и проверяю каждую правку до выката.
